   54 /// Read a row's persisted state and validate a transition to `to` against the
   55 /// frozen domain state machine.
   56 ///
   57 /// The schema's named `CHECK` fences only prove a token is *in the
   58 /// vocabulary*; this guard is what proves a write is a *legal* move
   59 /// (`docs/architecture.md` 搂8). It selects the row's `state` and, when the row
   60 /// exists and the target differs, runs `transition` (the domain machine) on
   61 /// `(current, to)`. A write whose target equals the persisted state is an
   62 /// idempotent *data* update (e.g. pid/health/progress while the lifecycle
   63 /// state is unchanged), not a transition: the frozen machine defines no
   64 /// self-loops, so same-state writes are accepted without consulting it.
   65 /// `ErrorCode::InvalidStateTransition` is returned when the domain machine
   66 /// rejects a transition or a guarded write affects 0 rows; an undecodable stored state is surfaced
   67 /// as `Internal`.
   68 ///
   69 /// Returns the **current** state when the row exists, or `None` for a
   70 /// first-seen row (no prior state, so a legal initial state may be written and
   71 /// no transition check applies). Callers then issue a write guarded on the
   72 /// returned state (`UPDATE ... WHERE <state_col> = <returned>`) and must check
   73 /// `rows_affected`: the guarded update is a compare-and-set, so a row that
   74 /// moved concurrently affects 0 rows and the write is rejected, even though
   75 /// the SELECT and the UPDATE are separate statements (a transaction is not
   76 /// required for the guard to be safe). Callers pass a re-usable executor (a
   77 /// pool handle, `Copy`); on a transaction connection a non-`Copy` executor
   78 /// cannot be used twice, so the caller performs the single guarded `UPDATE`
   79 /// inline (the transaction's own read supplies `expected`).
   80 async fn validate_state<'c, E, S>(
   81     exec: E,
   82     table: &str,
   83     key_col: &str,
   84     key: &str,
   85     to: S,
   86     transition: fn(S, S) -> Result<S>,
   87 ) -> Result<Option<S>>
   88 where
   89     E: sqlx::Executor<'c, Database = Sqlite> + 'c,
   90     S: std::fmt::Debug + Copy + PartialEq + Send + serde::de::DeserializeOwned + 'c,
   91 {
   92     let sql = format!("SELECT state FROM {table} WHERE {key_col} = ?1");
   93     let current: Option<String> = sqlx::query_scalar(&sql)
   94         .bind(key)
   95         .fetch_optional(exec)
   96         .await
   97         .map_err(|e| storage_error(&e, &format!("read {table} state")))?;
   98     match current {
   99         None => Ok(None),
  100         Some(raw) => {
  101             let current = parse_wire::<S>(&raw, &format!("{table}.state"))?;
  102             if current != to {
  103                 transition(current, to)?;
  104             }
  105             Ok(Some(current))
  106         }
  107     }
  108 }

  157 3. 做资源预检。若明显不足且策略允许，选择 idle LRU victims，依次 drain/unload。
  158 4. 以独立 process group 启动子进程，同时采集有界 stdout/stderr ring buffer。
  159 5. 等待 health endpoint，采用启动 deadline；同时监控子进程退出。
  160 6. health 成功后读取 `/v1/models` 校验标识，再原子发布为 `ready`。
  161 7. 若疑似 OOM，且尚未进行过驱逐重试，则驱逐 idle victims 后只重试一次。
  162 8. 失败时终止残留进程、释放端口 reservation、记录结构化失败原因。
  163 
  164 避免“端口先检查后被占用”的竞态：daemon 应持有 listener reservation，或让子进程在受控端口范围内失败重选；具体方式在实现 spike 中确定，因为现有引擎不能继承监听 socket。
  165 
  166 ## 6. 显存切换策略
  167 
  168 - `deny`：资源不足立即失败。
  169 - `auto_evict_idle`：默认；按 `last_used_at` 从旧到新驱逐 idle 实例。
  170 - `replace_instances`：调用者显式给出可卸载的 instance IDs，最可预测。
  171 
  172 active request 是硬保护条件。加载 operation 使用全局 resource lock 串行化，避免两个并发 load 各自依据相同空闲显存做决定。MVP 假设单 GPU；数据模型保留 `device_ids`。
  173 
  174 失败识别不能只依赖 stderr 文案。建议记录：进程 exit code、stderr tail、启动前后 `nvidia-smi` snapshot、是否出现 health、deadline 阶段。只有 `FailureClass::GpuOomLikely` 才自动驱逐重试，其他错误直接失败。
  175 
  176 ## 7. 推理请求路径
  177 
  178 1. 认证、body size、并发限制。
  179 2. 对需要路由的请求只解析 `model`，保留原始 JSON 字段。
  180 3. 从内存 registry 获取 `ready` instance lease；lease 增加 `active_requests`。
  181 4. 将请求发送到 loopback upstream。必要时将外部 bearer token 替换为 runtime 私有 token。
  182 5. 普通响应透传状态、body 和允许的 headers；SSE 以流方式转发，不缓冲完整响应。
  183 6. 完成、错误或客户端断开均释放 lease，并更新无正文 metrics。
  184 
  185 同一 model key 若未来存在多个实例，采用 least-active + round-robin tie-break。首版通常是一对一。
  186 
  187 ## 8. 进程恢复和退出
  188 
  189 - daemon 启动时将数据库中非终态实例标记为 `crashed/recovery_required`。
  190 - 首版不 attach 到未知 PID，避免 PID reuse 和错误终止其他进程。
  191 - daemon 正常退出时停止接收管理操作，drain inference，然后终止其监管的全部子进程。
  192 - 可选的 `restore_on_start` 后续实现；首版服务重启后由用户重新 load。
  193 - 子进程意外退出不会无限重启；记录 crash 并等待显式 load，防止 OOM crash loop。
  194 
  195 ## 9. 一致性和并发控制
  196 
  197 - per-model mutex：防止同一模型同时 load/unload。
  198 - global resource mutex：串行 GPU placement/eviction/load commit。
  199 - instance lease：保护有活动请求的实例不被自动驱逐。
  200 - SQLite transaction：operation、instance desired state 和 audit event 同步提交。
  201 - 内存 registry 是路由真相；SQLite 用于恢复和审计，不位于 inference 热路径。

   65 ## 3. 核心领域对象
   66 
   67 ### Model
   68 
   69 - `id`：内部稳定 UUID。
   70 - `key`：API 使用的唯一可读标识，扫描时生成，允许管理员覆盖。
   71 - `path`：canonical absolute path。
   72 - `artifact_kind`：`gguf | ninfer`。

   77 
   78 ### Runtime
   79 
   80 - `id`、`kind`、`executable_path`。
   81 - `enabled`、`version_text`、`capabilities`。
   82 - runtime 固定参数模板；不允许存储任意 shell command。
   83 
   84 ### Instance
   85 
   86 - `instance_id`：一次加载实例的唯一标识，同时用于 LM Studio unload。
   87 - `model_id`、`runtime_id`、resolved load config。
   88 - `state`、`pid`、`port`、`started_at`、`last_used_at`。
   89 - `active_requests`、`health`、`failure`。
   90 
   91 数据库保存实例记录和期望状态，但 PID/port 只有进程监管器确认后才可信。
   92 
   93 ### Operation
   94 
   95 load/unload/rescan 是可能耗时的 operation：`queued | running | succeeded | failed | cancelled`。内部管理 API 默认返回 `202 + operation_id`，Web UI 通过 SSE 订阅进展。LM Studio 兼容 load 为满足其同步响应约定，会等待 operation 结束或到达专用长超时。
